# Code-first game workflow

## 每款游戏的最小交付

一个游戏一个 `games/<slug>/` 目录，保存入口、规则、素材、运行说明和验收记录。根目录索引只放名称、路径、当前阶段与试玩链接。个人主页和学术项目继续使用原有目录及部署配置。

## 从优秀案例借鉴什么

本次参考已有 Loopit 创作 skill 中的 Color Alchemy、Easy Game 等案例记录，而非把历史评级当作当前市场保证。落实为三件可验证的事：

1. **动作与结果直接对应**：按住时弧线和落点移动，松开后肉饼沿相同轨迹飞行。
2. **失败提供下一次尝试的信息**：投短提示多蓄力，投远提示更早松手。
3. **完成后有明确回合闭环**：三单获胜或三次失误失败；重开后状态复位，可以再次操作。

## 生产顺序

1. 写清一个核心动作、目标、失败条件和重玩理由。
2. 先写规则与状态转换，再接图片和动画；反馈动画不能偷偷改分。
3. 本地验证正常结束、失败、重开、输入取消与小屏布局。
4. 只上传该游戏所需的资源，提交到游戏专用分支，检查变更均在 `games/`。
5. 向 Loopit 提供固定 commit 的源码目录和接入约定，要求只做必要的宿主适配。
6. 分别验收 Loopit 编辑器和独立试玩页。AI 的“已完成”消息不等于测试通过。
7. 发现偏差时记录触发动作、期望、实际值、版本和应保留的内容，再做小范围修复。
8. 以验证过的版本更新索引和验收记录。展厅发布单独按用户授权执行。

## 本次实验得到的实际经验

- GitHub 固定源码与七张透明 PNG 已进入 Loopit V1：平台声明已读取源码，真实画面也出现对应素材；资源清单显示七张图片已被打包到平台 CDN。
- 原始代码本地通过三单 450 分通关、三次失误、两种结算后重开和空格输入。
- V1 适配曾出现低帧率下 605ms 按住只得到约 4% 蓄力；本地最终松手值约 43%。因此应在释放时根据单调时钟计算最终蓄力，不能仅依赖 RAF 累加。
- 小屏还出现根容器宽度与滚动条相互挤占，证明“已适配竖屏”必须用真实 DOM 尺寸和截图核对。
- 修复与最终验收记录放在游戏自己的 `EXPERIMENT_LOG.md`，不要把本地通过误记成平台通过。

这些是一次具体接入实验的经验，并非所有游戏或未来 Loopit 版本的保证。
