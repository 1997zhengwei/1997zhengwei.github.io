日期：2026-11-13，Windows / IAB。本报告记录上传前的本地验收。用户随后已授权 GitHub 中文目录及 Loopit 初稿；平台验证另行记录，历史开发备份留在本地。

## 用户修正与实现

用户要求一种鱼只保留一个鱼缸，扩建时让原缸本身变大。已移除 v0.3 的重复展缸和长廊段生成：六种鱼最多六个独立展缸。升级提高原缸的宽度、高度、容量和售价；水体、底砂、饰边、鱼群游动范围及标签高度同步变化，缸体用平滑动画扩大。

缸内侧边缘和中央补货位置保持固定，缸向外生长。高等级横向增幅渐缓，高度继续增长，避免六缸互相重叠或侵占中央道路。顾客容量由营业总容量、馆级与宣传共同提高。已获授权的稀有鱼、财富陈列、称号、清蓝海水及玻璃廊保留。

v0.3 旧档迁移：同鱼种库存和稀有库存相加，总容量保留，最高单缸等级保留，其余升级投入转换为永久容量及馆级历史积分；永久珍藏重定向回本鱼种主缸。旧长廊上的角色安全回到原馆，携带物保持。新格式 growthVersion=2，重复保存不会再次合并。

## 53 项规则检查与构建

npm test：53/53 通过。保留原经营、上下岸、稀有捕捞/售卖、助手、荣誉和财富检查，替换已取消的重复缸预期，新增当前需求验收：

- 扩建指定原缸扣费，保持只有六种定义，不生成第七个缸；拒绝空目标、未知目标、未开放鱼缸及资金不足。
- 连续 80 次合法升级依旧只有六缸，容量和高度继续增长。
- 六缸达到 120 级时互不重叠，不越过岸边或外边界，中央通道和六个补货点均可达。
- 扩大后的满缸重新腾出容量，可补入真实鱼，并按升级后的售价卖出，不凭空生成库存。
- 旧重复缸合并保留总容量、普通/稀有库存、等级、称号对应馆级、背包与永久珍藏；多次保存恢复幂等。规则样本验证 33 条合并库存与 3 条稀有子库存等非零情形，不冒充浏览器另有非零旧库存迁移实测。
- 新几何、历史容量和稀有携带物存档恢复；扩大时处于新缸范围内的角色移到安全位置，背包不丢失。
- 只有一个鱼缸时，升级容量也能提高客流；扩大后仍可追踪移动的珍稀鱼。

初轮唯一失败为浮点数边缘坐标使用严格相等断言，改为数值容差后全套通过；没有以降低玩法验收条件规避失败。
